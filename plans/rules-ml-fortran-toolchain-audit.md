# Existing rules_fortran and rules_ml_toolchain boundary

Source audit, 2026-11-16. `google-ml-infra/rules_ml_toolchain` main at [`9ff8598c`](https://github.com/google-ml-infra/rules_ml_toolchain/tree/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd), which pins `miinso/rules_fortran` at [`f0cac73e`](https://github.com/miinso/rules_fortran/tree/f0cac73ebdcbda7bc01b38b8a4ee33869416c220). The upstream source files and one published Flang archive were inspected; no new Bazel end-to-end build was run for this audit.

## Stock rules_fortran

Its [module extension/repository rule](https://github.com/miinso/rules_fortran/blob/f0cac73ebdcbda7bc01b38b8a4ee33869416c220/fortran/repositories.bzl) downloads `miinso/flang-releases` host archives and exposes compiler, archiver, runtime libraries and compiler files. Its [Linux x86_64 toolchain](https://github.com/miinso/rules_fortran/blob/f0cac73ebdcbda7bc01b38b8a4ee33869416c220/fortran/toolchains/BUILD.bazel) uses `flang-new` as both compiler and linker, `llvm-ar` as archiver, packaged runtime libraries, and `-lm -lpthread`. It does not declare a Linux libc sysroot. Its [binary rule](https://github.com/miinso/rules_fortran/blob/f0cac73ebdcbda7bc01b38b8a4ee33869416c220/fortran/private/fortran_binary.bzl) runs a custom link action, with `use_default_shell_env = True`; it does not use `cc_common.link` for that final action. Therefore the stock native Linux Flang-driver link has no source-declared target libc/CRT closure and may use host/default search paths. Its [library rule](https://github.com/miinso/rules_fortran/blob/f0cac73ebdcbda7bc01b38b8a4ee33869416c220/fortran/private/fortran_library.bzl) propagates the archive and runtime through `CcInfo` for C/C++ consumers.

Downloaded the published [`v21.1.8` Linux x86_64 archive](https://github.com/miinso/flang-releases/releases/tag/v21.1.8) to `/tmp/flang-archive-audit/` and listed its 1,980 tar entries. It contains `bin/flang-21` with `flang`/`flang-new` symlinks, `llvm-ar`, target `include/flang/*.mod`, `libflang_rt.runtime.a`, `libclang_rt.builtins.a`, compiler CRT begin/end objects, libc++/unwind/OpenMP archives and headers. It contains no `libc.a`, `libc.so`, `crt1.o`, `crti.o`, `ld-linux*`, `sysroot/`, or `usr/include/` path. `file` reports the extracted `bin/flang-21` is statically linked ELF; `llvm readelf -d` shows no dynamic section. The host compiler itself does not need a preinstalled Linux libc to execute, but the archive does not close the target libc side of a Flang-driver link.

## Google ML integration

Its [patch to rules_fortran](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/third_party/rules_fortran/toolchains.patch) removes the stock Flang repository extension/registrations and aliases the ruleset's toolchain type to `@rules_ml_toolchain//fortran:toolchain_type`. Google ML owns [six registered execution/target pairs](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/fortran/BUILD). Downstream roots must copy/apply that patch and register the Google ML toolchains; the [README](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/fortran/README.md) requires LLVM 20+ for Fortran and documents `LLVM_VERSION` and `SYSROOT_DIST` selection.

For Linux, [toolchain_deps.bzl](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/common/deps/toolchain_deps.bzl) downloads two distinct assets: an official LLVM/Flang distribution such as LLVM 21.1.8 Linux X64, and a versioned glibc/GCC sysroot tarball such as Ubuntu 20 GCC 10/glibc 2.31. The [LLVM BUILD overlay](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/common/config/llvm21_linux_x86_64.BUILD) expects `bin/flang`, intrinsic modules under `include/flang`, Flang-RT and FortranDecimal archives, Clang++, LLD, archiver, builtins and C++ libraries. The [sysroot BUILD overlay](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/common/config/x86_64_ubuntu20_gcc10/sysroot.BUILD) declares `usr/include`, CRT objects, `libc.a`/`libc.so`, libm, pthread, libgcc, libstdc++ and related libraries. The Linux target libc is **downloaded as a Bazel repository, not assumed installed on the build host**.

The [Linux Fortran implementation](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/fortran/impls/linux_x86_64_linux_x86_64/BUILD) passes Flang, matching modules/runtime, Clang++, LLD, archiver and the downloaded sysroot to a [Fortran toolchain provider](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/fortran/toolchain.bzl). That rule obtains the selected C++ toolchain, derives its executable link flags via `cc_common.create_link_variables` and `cc_common.get_memory_inefficient_command_line`, and packages the Fortran runtime as `CcInfo`. The underlying `rules_fortran` binary rule then runs its **own Clang++ action** with those flags and explicit runtime libraries. This is a third shape: ruleset-owned link action using the CC toolchain's environment. It is not `cc_common.link`, and on Linux it is not a Flang-driver link. The [Windows Fortran implementation](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/fortran/impls/windows_x86_64_windows_x86_64/BUILD) instead selects Flang as linker.

The README's blanket hermeticity claim needs platform qualification. Its [macOS SDK repository rule](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/cc/sysroots/macos_sdk.bzl) uses `MACOS_SYSROOT_PATH` or host `xcrun` and symlinks the local SDK. Its [Windows MSVC repository rule](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/cc/sysroots/windows_msvc.bzl) explicitly discovers host Visual Studio/MSVC and SDK environment. Linux CI runs in a [pinned container](https://github.com/google-ml-infra/rules_ml_toolchain/blob/9ff8598c6dfa182f4fd49f9af761c67bc2e50abd/.github/workflows/fortran_linux_x86_64_linux_x86_64_tests.yaml). This audit confirms source-declared Linux **target** libc inputs; it has not inspected the host ELF dependency closure of Google's downloaded upstream LLVM binary or proved absence of all host reads in its custom link action.

## Implication for our design

A complete hermetic link environment need not be one Flang archive. It can compose a minimal, host-static Flang compiler archive with matching target Flang modules/runtime and Hermetic LLVM's existing target libc/CRT/builtins/LLD inputs. Google ML demonstrates separate downloaded compiler and sysroot assets, while stock rules_fortran's bundle does not solve the target libc requirement. The first qualified path remains `cc_common.link`; a future ruleset-owned manual Clang++ link action or Flang-driver link needs its own declared inputs and link-command qualification. This audit does not authorize a new public API or publication.
